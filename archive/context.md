## Удалённое управление через Python Server

Isaac Sim можно дёргать **снаружи**, из Jupyter notebook, пока открыто окно с GUI.

**Включить расширение** (один раз на сессию, внутри Isaac Sim):
`Window → Extensions` → найти `isaacsim.code_editor.python_server` → включить тумблер. Открывает TCP-порт `8226`.

**Рабочий код клиента** (используется в `drone_control.ipynb`):

```python
import asyncio
import json

async def execute_in_isaac(source: str, host: str = "127.0.0.1", port: int = 8226) -> dict:
    """Отправить код на выполнение в уже открытый Isaac Sim и получить результат."""
    reader, writer = await asyncio.open_connection(host, port)
    writer.write(source.encode())
    writer.write_eof()
    data = await reader.read()
    writer.close()
    return json.loads(data.decode())
```

**Важно:** в Jupyter уже есть свой event loop, поэтому вызывать нужно `await execute_in_isaac(code)` напрямую в ячейке, а НЕ через `asyncio.run(...)` — это даст `RuntimeError: cannot be called from a running event loop`.

Формат ответа: `{'status': 'ok'|'error', 'output': str, 'result': ..., 'traceback'/'ename'/'evalue' при ошибке}`.

Состояние Python (переменные, импорты) сохраняется между вызовами в рамках одной сессии Isaac Sim.

### Важный концепт: вращение ≠ полёт

PhysX не считает аэродинамику сам. Вращение `m1_joint`...`m4_joint` крутит пропеллер визуально и физически (как мотор), но **не создаёт подъёмную силу автоматически**. Чтобы дрон взлетел — на каждый пропеллер дополнительно нужно прикладывать силу (Force) вверх, пропорциональную тяге мотора. Это отдельная задача — расчёт тяги (thrust) и приложение силы через physX API.

### Рабочий код: раскрутка моторов (Drive)

```python
import omni.usd
from pxr import UsdPhysics

stage = omni.usd.get_context().get_stage()
joint_paths = [
    "/World/cf2x/body/m1_joint",
    "/World/cf2x/body/m2_joint",
    "/World/cf2x/body/m3_joint",
    "/World/cf2x/body/m4_joint",
]

TARGET_VELOCITY = 1500.0  # градусов в секунду

for path in joint_paths:
    prim = stage.GetPrimAtPath(path)
    drive = UsdPhysics.DriveAPI.Apply(prim, "angular")
    drive.CreateTypeAttr("force")
    drive.CreateTargetVelocityAttr(TARGET_VELOCITY)
    drive.CreateDampingAttr(1e5)
    drive.CreateStiffnessAttr(0.0)
```

**Объяснение параметров Drive:**
- `stiffness = 0` — не держим конкретный угол (не позиционный режим)
- `damping` — большое число → сустав ведёт себя как мотор, стремящийся держать заданную **скорость** вращения
- `targetVelocity` — целевая скорость в градусах/сек (конвенция USD Physics для Revolute Joint)

**Запуск симуляции (обязательно, иначе физика не считается):**
```python
import omni.timeline
omni.timeline.get_timeline_interface().play()
```

✅ Протестировано и работает — пропеллеры визуально раскручиваются.

### ❌ Грабли #1: сила на лёгкие звенья (пропеллеры)

Прикладывание силы тяги напрямую к `m1_prop`...`m4_prop` (масса ~0.0008 кг каждый) вызывает огромное ускорение на лёгком звене относительно сустава (`a = F/m`) → сустав "срывает", дрон хаотично крутится.

**Исправление:** силу прикладывать к **`body`** (тяжёлый, стабильный — 0.025 кг), но **в точке расположения** каждого пропеллера. PhysX сам считает подъёмную силу + момент через офсет точки приложения от центра масс.

### ❌ Грабли #2: все 4 пропеллера крутятся в одну сторону

Если все суставы (`m1_joint`...`m4_joint`) получают **одинаковый знак** `targetVelocity` — реактивный момент (3-й закон Ньютона: мотор крутит пропеллер → корпус толкает в обратную сторону) **не компенсируется** между моторами и накапливается → дрон взлетает нормально, но постепенно "штопорит" по рысканью (yaw), раскручиваясь всё сильнее.

**Исправление:** чередовать направление по диагонали, **в соответствии с названиями мешей** в самой структуре дрона (`ccw_prop` / `cw_prop`):
```python
joint_directions = {
    "m1_joint": +1,  # ccw_prop
    "m2_joint": -1,  # cw_prop
    "m3_joint": +1,  # ccw_prop
    "m4_joint": -1,  # cw_prop
}
```
Так у настоящих квадрокоптеров и устроено — соседние/диагональные моторы крутятся в разные стороны именно для гашения реактивного момента.

### ❌ Грабли #3: постоянная одинаковая тяга на всех моторах нестабильна

Даже с исправленными направлениями вращения — чистая постоянная тяга без обратной связи рано или поздно "штопорит". Квадрокоптер физически неустойчив сам по себе (любая микроасимметрия накапливается со временем). Реальные дроны летают только благодаря быстрому контроллеру, постоянно подруливающему моторами.

### Решение: PD-стабилизация (самовыравнивание)

Измеряем наклон корпуса через направление его локальной оси Z в мировых координатах (`transform.TransformDir(Gf.Vec3d(0,0,1))`) — если дрон стоит ровно, вектор `(0,0,1)`; любое отклонение по X/Y = наклон в эту сторону.

На каждом моторе тяга корректируется пропорционально наклону и скорости наклона (классический PD-регулятор):
```python
correction = KP_TILT * (tilt_x * ox + tilt_y * oy) + KD_TILT * (d_tilt_x * ox + d_tilt_y * oy)
force_n = max(0.0, base_force + correction)
```
где `(ox, oy)` — смещение мотора от центра масс корпуса (узнаётся автоматически из позиций в сцене, не хардкодится).

`KP_TILT`, `KD_TILT` — коэффициенты регулятора, подбираются экспериментально (как тюнинг PID на реальных дронах). Стартовые значения: `KP_TILT=0.45`, `KD_TILT=0.06`.

### ✅ Рабочие коэффициенты (подтверждено тестом — плавный взлёт без раскрутки)

```python
KP_TILT = 0.03   # пропорциональный
KD_TILT = 0.0    # дифференциальный пока не нужен, P-части достаточно для плавного взлёта
```

Изначальные `KP_TILT=0.45, KD_TILT=0.06` были слишком агрессивными — вызывали резкий толчок одним пропеллером, потом противоположным, маятник и раскрутку (классическая нестабильность от слишком высокого коэффициента усиления). Уменьшение в ~15 раз решило проблему.

Также важная мелкая правка: `_prev_tilt` (для D-части) должен обновляться **каждый** физический шаг, а не только когда газ включён — иначе в момент включения газа получается ложный скачок производной (если `_prev_tilt` долго "стоял" на старом значении).

**Статус: дрон стабильно и плавно взлетает с этими коэффициентами. Можно постепенно увеличивать KP/добавлять KD для более резкой реакции на возмущения, если понадобится.**

### ❌ Грабли #4: добавление D-части ухудшило стабилизацию

При `KD_TILT=0.01` дрон стал лететь хуже (раскачка началась раньше, на высоте ~2 корпусов вместо большей высоты с чистым P). Причина: числовое дифференцирование (`d_tilt = (tilt - prev_tilt) / dt`) сильно усиливает любой мелкий шум в измерениях при делении на маленький `dt` — классическая проблема D-регуляторов на зашумлённом сигнале.

**Подозреваемый источник шума:** визуальное вращение пропеллеров на `1500°/сек` через "жёсткий" Drive (`damping=1e5`), оставшееся с самого первого теста ("раскрутить пропеллеры"). Оно не нужно для тяги (сила прикладывается напрямую через `apply_force_at_pos`, независимо от вращения сустава), но создаёт постоянное взаимодействие с решателем физики.

**Исправление:** `targetVelocity=0` на всех суставах (Drive остаётся, но не крутит), `KD_TILT` обратно в `0`. Проверяем, станет ли чистый P стабильнее без этой "тряски".

### ✅ Геометрический контроллер (адаптация Pegasus Simulator)

Вместо самодельного P/PD на "вектор вверх" — портировали проверенную математику из Pegasus (`QuadraticThrustCurve`, `NonlinearController`, allocation-матрица из `multirotor.py`). Это академический геометрический регулятор (Lee/Mellinger/Kumar), который правильно считает ошибку ориентации через матрицы поворота (SO(3)), а не упрощённо через один вектор.

**Единственное, что заменили** относительно оригинала Pegasus (у которого ядро физики `dynamic_control` не работает на нашей версии):
- Чтение состояния (позиция/ориентация/скорости) — напрямую из USD-сцены (`UsdGeom`, `UsdPhysics.RigidBodyAPI`) вместо `get_dc_interface()`
- Позиции моторов для allocation-матрицы — из наших `PROP_OFFSETS_XY` вместо `get_relative_body_poses()`
- Приложение силы/момента — наш уже рабочий `apply_force_at_pos` / `apply_torque` вместо `dynamic_control`

Сам алгоритм (двухконтурный: позиция → желаемая ориентация → момент → микшер на 4 мотора) — один в один из Pegasus.

**Важные детали реализации:**
- Угловая скорость в USD хранится в **градусах/сек**, нужно переводить в радианы для математики контроллера (`np.radians(...)`)
- Сила прикладывается вдоль **локальной оси Z корпуса** (через `world_up`), а не вдоль мировой Z — корректно учитывает наклон
- Реактивный момент по рысканью (yaw) — отдельный вызов `apply_torque`, так как вертикальная сила сама по себе момент по Z не создаёт
- Упростили относительно оригинала: вместо слежения за траекторией — простое удержание точки (зависание), с управлением высотой через `adjust_height()`/`set_height()`

**Коэффициенты регулятора** пересчитаны пропорционально массе (дрон ~28г против ~1.5кг в примере Pegasus) — это начальная оценка, может потребовать донастройки:
```python
Kp=(0.2, 0.2, 0.2), Kd=(0.16, 0.16, 0.16), Ki=(0.03, 0.03, 0.03)   # позиция
Kr=(0.003, 0.003, 0.003), Kw=(0.0006, 0.0006, 0.0006)               # ориентация
```

Управление:
- `start_motors()` — включить контроллер (целится в текущую позицию +0.5м по высоте)
- `adjust_height(±N)` / `set_height(N)` — менять целевую высоту
- `kill_motors()` — аварийный стоп

**Диагностика печатается внутри Isaac Sim, не в notebook!** `print()` внутри `_on_physics_step` выполняется асинхронно после завершения вызова `execute_in_isaac`, поэтому вывод идёт в лог-файл Isaac Sim:
```

```
Самый свежий файл по времени изменения. Искать через `grep "p=\[" <файл>` — там будут наши строки с `p=`, `F_des=`, `tau=` и т.д.

### Итерации настройки коэффициентов

1. **Kp=0.2, Ki=0.03, Kr=0.003** (оценка по массе) — резкий хаотичный рывок в случайную сторону. Подозреваем **integral windup** по позиции (`Ki` без ограничения, накапливается бесконечно)
2. **Kr=0.0003, Kw=0.0001, Ki=0** — старт идеально ровный (`e_R=0, tau=0` на первом шаге), но дальше `e_R` стабильно растёт, а `tau` исчезающе мал (~1e-6) — коррекции категорически не хватает
3. **Kr=0.0012, Kw=0.0004** — взлетает ровно ~4 корпуса высоты, потом всё равно уводит дугой. Рост `e_R` почти не замедлился несмотря на 4x прирост `tau` — подозрительно
4. **Тест-гипотеза: убрать Drive с суставов полностью** (свободные суставы вместо жёсткого лока через артикуляцию) — **не подтвердилась**, паттерн снова идентичен. Жёсткая стыковка корпус-пропеллер исключена как причина
5. **Kr=0.012, Kw=0.004** (x10 от попытки 3) — раскачка во все стороны как качели, перелёт через цель и случайное падение. Классическая недостаточная демпфировка при высоком усилении
6. **Kr=0.004, Kw=0.003** (вилка между попытками 3 и 4, относительно больше демпфирования) — качели пропали, взлёт стабильный первые ~10-15 физических шагов (`e_R` маленький, `rotor_vel` у всех 4 моторов почти одинаковый ~768 рад/с). Но дальше в логе видно **насыщение `rotor_vel`** — упирается то в `0`, то в потолок `1100`. Разобрали причину: `THRUST_HEADROOM=2.2` даёт на зависании скорость мотора `1/sqrt(2.2)≈67%` от `MAX_ROTOR_VELOCITY` — почти нет запаса на дифференциальную тягу для коррекции крена/тангажа. Как только `e_R` чуть подрастает, allocation-матрица требует разницу скоростей моторов больше, чем физически доступно → насыщение → асимметричная тяга → разгон вращения (особенно по yaw, `e_R[2]` доходил до ~0.3) → коллапс. Причина НЕ в гейнах, а в нехватке запаса тяги (actuator saturation)

Прямое перемножение `w×(I_DIAG·w)` смешало две системы координат — вместо маленькой коррекции получилась заметная ПОСТОЯННАЯ ошибочная сила в одну сторону

То есть `tau = -(Kr@e_R) - (Kw@e_w)` складывал body-frame `e_R` с world-frame `e_w` — рассинхрон, который растёт именно с углом наклона (при малом наклоне world≈body, ошибка пренебрежима — ровно поэтому все попытки 1-12 с маленькими углами не показывали проблему так явно, а она проявлялась только когда `e_R` дорастал до 0.1+ рад). Это первый найденный кандидат, объясняющий ИМЕННО рост ошибки именно при заметных, не очень малых углах — то самое нелинейное при заметных углах несоответствие из попытки 36

## Восстановление среды после переезда на новый диск (28.06.2026)

### Ситуация
Проект переехал на новый диск (C:). Старая система осталась на D: (полный Windows + Programs). Папка `C:\VSCODE\ISAAC\` была скопирована с D: вместе с `isaac_env` (17.4 GB — все пакеты на месте: isaacsim, torch, jupyter, mavlink и т.д.). Notebooks (`drone_control_12.ipynb`, `drone_control_65.ipynb`) тоже скопированы.

### Проблема
`isaac_env` — venv, привязанный к базовому Python по абсолютному пути в `pyvenv.cfg`:
```
home = C:\Users\DOM\AppData\Local\Programs\Python\Python312
executable = C:\Users\DOM\AppData\Local\Programs\Python\Python312\python.exe
version = 3.12.7
```
На новой системе Python 3.12.7 не был установлен — venv не активировался.

### Решение
1. Установили **Python 3.12.7** (64-bit) для текущего пользователя — стандартный установщик с python.org, опция "Install for current user only" → Python ставится именно в `C:\Users\DOM\AppData\Local\Programs\Python\Python312\`, путь совпадает с `pyvenv.cfg` → venv ожил без переустановки пакетов.
   - "Add python.exe to PATH" — **не отмечено** (не нужно, venv используется напрямую)
   - "Install for all users" — **не отмечено** (не нужны права администратора)

2. **ExecutionPolicy** — при попытке `.\isaac_env\Scripts\activate` PowerShell выдал ошибку "выполнение сценариев отключено". Исправлено командой (запускать в своём терминале, без прав администратора):
   ```powershell
   Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
   ```
   После этого `.\isaac_env\Scripts\activate` работает нормально.
